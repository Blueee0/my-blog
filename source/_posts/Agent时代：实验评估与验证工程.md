### 一、**从确定性工程思维，转向科学的实验思维**

1. **评估指标比工程设计更重要**

   在面对具体问题时，应该先确定评估指标，然后再进行A/B测试来判断策略的有效性。

   **Ex：客服对话类App**

   人均对话轮次、聊天时长这些指标没办法直接跟 AI 效果挂钩。用户跟 AI 连续聊了十几个来回，到底是因为很满意，还是因为 AI 一直没帮用户解决问题？

   - 人工评估：准是准，但太贵太慢了，没办法覆盖全量流量，灵敏度就会很差；
   - LLM-as-a-Judge：每条对话都要逐字把评语写出来再打分，Token 成本太高，而且打分极易受 Prompt 影响；
   - 微调专用裁判模型：每次底座模型一升级，就得重新准备海量标注数据再训一遍，现在 Qwen4 都快出了，微调裁判还停留在 Qwen2.5，评估模型永远比被测的模型旧。

   **最终的工程方案**：不去调整基座模型参数，也不让模型输出评语，而是直接把模型内部的隐藏状态里的分数投射出来。

2. **不要直觉判断，一定要做对照实验**

   **Ex案例：**让大模型给同一段对话打分，有三种 Prompt 写法，分别是“先写理由再打分”“先打分再写理由”和“只给分数不写理由”，哪一种最准？现场大部分人都选了“先写理由再打分”。

   **实验结果：**该团队拿线上真实会话样本跑完对照实验，结果跟所有人的直觉完全相反：在 Qwen3-4B 上，只打分不写理由的效果最好；到了 Qwen3-Max，先打分再写理由的效果最好；换到 Qwen2.5，结果又不一样了，**没有任何一种 Prompt 写法能在不同模型上稳定胜出。**

   **原因分析：**大模型的 Decoding 机制上。模型前面生成的 Token，会直接改变后面打分的概率分布。哪怕模型刚读完对话时，内部状态已经认定是 5 分，可一旦让它长篇大论写理由，它顺着往下挑点小毛病，写着写着就把自己说服成了 4 分，最后吐出来的分数全变了。这组对照实验直接把微调打分提示词的方案淘汰了：只要靠生成文字来打分，分数就会跑偏。

3. **最终的工程实验（作出假设、设计并执行实验）**

   他们团队提出了一个假设：**模型在 Prefill 阶段读完原文和评分标准时，内部其实已经有了评分信号，不必等到 Decoding 阶段逐字吐出评语；不去调整基座模型参数，直接从最后一个 Token 的隐状态向量里就能把分数投射出来。**

   围绕这个假设，他们用三步实验跑通了闭环：

   1. 第一步，用**正负差分法**去除噪音，提取纯净的好坏信号。

      当时 Jev 模型还没出来，怎么从数千维、混杂着与评分无关的大量上下文噪音的隐向量里，单独提取出满意度信号？他们做了个差分对照实验：把同一段对话复制两份只做 Prefill 阅读，分别拼上正向引导（“这段对话整体是 5 分”）和负向引导（“这段对话整体是 1 分”），再把两次读出的隐向量直接相减。因为前面的对话完全一样，共同的噪音在相减时刚好抵消，剩下的差值向量就能干净地反映出模型对好坏的真实判断。

   2. 第二步，靠**统计分布挖掘捞出极端样本**，LLM归纳冷启动评分标准。

      线上 98% 的对话都是平庸的 3 分，1 分和 5 分的极端样本仅占 1%～2%。

      冷启动阶段，人工大海捞针写 Rubric 成本极高。

      他们先不设标准做了一轮盲测，观察差值向量的统计分布，发现极端好坏样本的向量模长更大、偏离质心更远，于是用极化指数自动从海量流量里捞出两头的极端案例，再交给大模型归纳出贴合线上真实分布的 Rubric。

   3. 第三步，**做消融实验验证模块贡献**，证伪无监督路线。

      要把数千维的差值向量映射成 1～5 分，他们通过严格的消融实验逐一验证：比如在降维回归头的选型上，如果把拿着人工打分做参照的有监督 PLS，替换成省事免标注的无监督 PCA，人类一致性会直接跌去三成以上，消融结果直接证伪了无监督路线。

   最终实验结果很有说服力：在同一张评测表上，Qwen3-4B 用这套打分方案，人类一致性和趋势相关性直接追平了 Qwen3-Max 的生成式打分；换成 Qwen3-14B，两项指标进一步提升约 10%。在同等规模的会话评测下，相比于 Qwen3-Max 生成式打分，这套方案的成本直接砍掉了 97%，吞吐量翻了近 8 倍。

### 二、大规模代码重构 - 建立工程体系做验证

1. **业务抽象（确保输入输出一致）**

   不看代码实现，只看对外行为是否等价。每一次业务调用抽象为一个四元组：

   - Input：接口的入参，比如查哪个机构、哪个户号；

   - Environment：代码执行依赖的前置状态，比如 DB 里的待支付账单、配置中心开关；

   - Side Effect：代码执行对外部系统产生的状态改变，比如写了一次 DB、调了一次外部机构接口；
   - Output：接口最终吐给上游的结果。

2. **测试用例（软件工程的测试方案）**

   - **第一步，通过静态分析与路径剪枝，收敛出高覆盖的测试用例。**

     他们先用静态代码分析工具提取老代码的控制流图 CFG，找出所有代码分支和业务结果，再让 AI 补充对应的业务语义。

     但如果把所有变量直接做排列组合，测试场景会呈指数级爆炸，根本测不过来。

     于是他们做了一层路径剪枝：只把共同决定同一个 if 分支的变量组合测试，互不影响的独立变量分开单测，再剔除掉逻辑上不可能同时成立的无效组合，在覆盖全部业务结果的前提下，把测试用例大幅收敛了几个数量级，压到了可执行的规模。

   - **第二步，用老系统黑盒引擎验真，隔离外部依赖并防 AI 作弊。**

     他们在测试抽查时发现两个棘手问题：一是 AI 生成复杂长链路用例如果反复报错，就会作弊把用例退化成在第一行参数校验直接返回；二是外部海量合作机构根本没有测试环境接口。

     他们基于现有的 Mock 基建，从老代码里提取出外部接口定义，把 DB 状态、配置和外部调用全部 Mock 隔离，搭了一套老系统黑盒执行引擎：先把 AI 生成的用例放进 Java 老代码里真实跑一遍，确认跑通了目标深层分支并拿到基准结果，再把这批高覆盖的可信用例放到 Rust 系统里循环回放，让 Coding Agent 自动修代码，直到两边结果完全对齐。

3. **不直接切流上线，先跑现网影子流量逐笔比对**

   即便线下全量用例都过了，他们依然不敢直接切流，因为线上众多外部机构的真实状态根本无法在线下穷举。于是在上线阶段，他们在生产环境起了一个 Rust 影子进程，把现网真实流量异步转发给 Rust 跑影子验证。Rust 进程不产生真实的外部写操作，只把两边运行生成的四元组行为实时录制到在线回归平台做核验。就在这个阶段，他们还真抓到了一个性能隐患：AI 写代码时打了一个超大对象日志，导致低频接口出现卡顿。只有影子流量比对 100% 一致、性能负载达标，才允许准出，再按机构、按用户、按接口做精细化切流。

4. **不盲目追求全量上线，逐步灰度**

   全系统所有接口里，从年初干到现在，真正完成全量切流上线的其实还不到 20%。除了资金安全必须渐进放量之外，一个很现实的工程约束是**验证周期受制于物理世界的业务周期**。比如像北方供暖这类季节性强的业务接口，上半年根本没有流量，必须等到年底天冷开栓了，现网才会有真实流量打进来跑影子验证。拿不到现网验证的证据，他们就绝不盲目下线老代码。

   **AI 写代码的速度不代表上线速度，真正的瓶颈，往往看验证工程做得有多深。**

### Agent长程任务

商汤科技一位技术专家关于长程复杂优化任务 Agent 工程实践的分享更加激进，把需要连续运行好几周的算子优化任务里，提出假设、执行实验到验证结果的整套闭环全都交给多 Agent 自主运转。

1. **Agent框架系统设计**

   实验启动前，人和主控 Agent 先把优化目标、修改范围、性能阈值、质量集和截止期限全部定好且中途不能调整，再把多 Agent 严格拆成四类角色：

   - 主控 Agent：只负责提出假设、分预算和派任务单，不写代码；
   - 实验 Agent：只管写代码、调参数，不允许判断自己的结果好坏；
   - 验证 Agent：由干净上下文的审核 Agent 和测试脚本组成，按任务标准做正确性、速度和质量的验收，同样不能改代码；
   - Reducer：只整理结果、更新下一轮要读取的共享状态，不改写其它数据和代码。

   到了执行层面，前期分析和结果审核可以多 Agent 并行，但**代码修改与跑测验证必须串行执行**，每次只改一处，防止多个 Agent 同时改代码导致无法归因。

2. **用 Git 式的事件溯源防上下文丢失**

   把跨轮次的状态流转改成了类似 Git Commit 的事件溯源机制：每次代码改动都必须写明父版本，生成不可变的 SHA 快照哈希，确保被验证和最终上线的是同一份代码；每一轮实验都像提交一次 Commit 一样，追加一条结构化的实验记录，写清基于哪个父版本改了什么、单层提速多少、整网结论如何。

   所有历史记录只追加不覆盖，后续修复只能基于旧版本提交新节点，严禁修改或删除已有的失败记录与原始测量数据。哪怕任务中断、换人或换 Agent 接手，只要顺着版本树和提交历史回放，就能完整还原每一轮的决策现场，随时复现任意版本。

3. **不把停止条件写进 Prompt，建立 CI/CD 式的分级验证与状态机硬熔断**

   > CI/CD是持续集成（Continuous Integration, CI）和持续交付/部署（Continuous Delivery/Deployment, CD）

   有了职责隔离和版本溯源，候选方案要想合入主线，还要**像代码走发布流水线一样通过从局部到整网的分级验证，并由状态机执行硬性熔断**：把停止条件直接硬编码进状态机，绝不写在提示词里让 Agent 自由发挥，一旦某个方向时间窗口到期、理论上限不足或整网质量下降，状态机立刻自动熔断终止，或升级交给人处理。
